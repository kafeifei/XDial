# 场景展开后主线程持续布局

## 现场证据

Debug 构建 `1790140599` 打开场景设置、展开包含六条规则的卡片后失去响应。
宿主持续消耗约一个 CPU 核心，主线程上的诊断请求也超时。
3 秒采样中，263 个主线程样本有 262 个位于 `GraphHost.flushTransactions`，
其下反复执行 `LazyLayoutViewCache` 的尺寸、放置与可见阶段更新。
采样未显示主线程等待 daemon、网络、磁盘或锁；这是 UI 布局更新无法收敛的现场证据。

## 修复候选

场景列表与每张展开卡片的规则列表原来各有一层 `LazyVStack`。
改成普通 `VStack`，使卡片的完整高度在一次布局中确定，移除这两层可见阶段和高度估计反馈。
线路与线路组的原生表格保持原实现。场景外观、配对、拖动排序和保存逻辑不变。

## 验证及边界

- 新 Debug 构建 `1790142245` 编译、签名与组件身份验证通过。
- `test/scenario_layout_test.py` 在独立进程中构造合成数据，检查展开、滚动、尺寸变化及状态更新；
  6 条与 100 条规则的检查通过。30 秒超时只终止测试子进程，不操作已有应用。
- `--check-scenario-layout` 使用从未显示的窗口，在重定位和正常应用生命周期前执行。
- 可选 `--user-configuration --scenario-name <name>` 只读现有配置，不允许 Keychain 弹窗、
  不创建密钥、不连接网络、不注册 helper、不写回配置。现场配置检查后密文哈希不变。
- 旧实现的离屏检查也能通过，说明该检查尚未覆盖现场卡死的全部窗口或事件条件。
  不把离屏通过表述为已复现并证明根因消除；新宿主的现场运行仍需单独验证。
- 覆盖安装保留了原卡死进程；磁盘更新本身不会解除旧进程中的布局循环。
  在未获重启授权前不退出宿主、不重启服务或改变其他通道。
